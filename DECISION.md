# Decision

Follow-up: [Jackin rewrite readiness](JACKIN_REWRITE_READINESS.md) evaluates current product requirements against these infrastructure results. Native OpenShell daemon ownership, live policy editing, and instant cleanup after test-process SIGKILL are not all existing Jackin user promises. The original full-contract result below is retained; the product analysis identifies which gaps actually gate a rewrite and which are implementation responsibilities.

**Do not start a Jackin integration that claims the complete requested runtime contract.** On the tested OrbStack ARM64 profile, released OpenShell v0.1.5 starts a prebuilt real coding-agent image, supports the basic development environment and lifecycle, and reaches a dedicated external Docker daemon. Docker, live project binds, Compose, and Rust Testcontainers all ran. Required behavior still fails for native same-path executable replacement, preservation of active connections during unrelated policy changes, and cleanup after forced test-client termination. Native companion ownership was not demonstrated. No Jackin code was changed. Edits, builds and tests were driven by experiment scripts through runtime APIs, not an authenticated coding-agent session; they establish runtime behavior only.

Docker Desktop, native Linux hosts, remote gateways, Kubernetes, and a dedicated daemon VM were not tested. Missing prerequisites are listed in the capability matrix. No profile meets **READY FOR AN INTEGRATION PROTOTYPE** for the complete requested requirements, and no production readiness is claimed.

## Answers to the objective

1. **Build before launch:** yes. Docker installed Claude Code in an image before OpenShell creation. Both 2.1.310 and 2.1.309 were reported by actual sandbox processes. Unchanged and forced image builds were run. Final images reuse the published, digest-pinned Construct role base but do not reproduce the complete Architect role.
2. **Ordinary sandbox without Docker:** yes. Docker CLI existed, but no socket, instance engine, Docker endpoint environment, registry config or daemon client credential was supplied. The attempted engine endpoint was denied. The host builder's Docker authority was not inherited by the sandbox.
3. **Selected dedicated engine:** yes, as **external daemon connectivity**. Scripts created a dedicated engine per instance, with distinct mTLS CAs and keys. OpenShell's documented TCP/TLS-passthrough rule carried the connection. Missing credentials and A's certificate presented with B's trusted CA were rejected by TLS.
4. **Docker, Compose and Rust Testcontainers:** yes for the exercised operations. Same-path runtime bind mounts exchanged files both ways. Compose built an application, waited for Redis health, connected services, served changed source, used fixed and automatic ports, and removed its application. Real Rust tests started Redis and exchanged data; success/panic cleanup worked. Forced process termination left Redis behind.
5. **Normal edit/build/test cycle:** local/offline tests and the first native network test work. Rebuilding a changed executable at the same real path succeeds, but its next protected network connection fails the integrity check; two changed-hash cycles were executed. A distinct output path passed, as did Rust compilation/tests in a Docker child. Both are explicitly separate workarounds. mbx's real executable path, not just a project symlink, must match policy.
6. **Ownership:** OpenShell owns its sandbox compute and supervisor. Experiment scripts own dedicated engines, trust material, outer mappings, shared project volumes, and remaining children. Stopping or deleting the sandbox did not remove those resources. Fixture cleanup is not OpenShell cleanup. The interrupted-provisioning test also left resources until the fixture owner removed them.
7. **Configuration versus missing capabilities:** configure a unique Docker `sandbox_label` for each gateway on a shared engine, retain resource admission, approve only experiment volumes, match file ownership, set non-secret tool homes, invoke the role hook as the main process, and allow service ports separately from Docker API access. Use external lifecycle ownership for the daemon. Distinct executable paths and frozen policy are workarounds. No source patch was built or applied.
8. **Platforms:** OrbStack ARM64 supports the demonstrated conditional slice. A separate packaged macOS ARM64 VM supports only the tested agent/build slice with an environment workaround. Neither establishes the full requested contract on that or another platform.

## Security and workflow boundaries

OpenShell's agent network policy denied the harmless endpoint at port 15434 while a child launched by the external daemon reached it. Docker children do not inherit the agent's OpenShell policy in this arrangement. A Docker grant conveys broad authority inside that dedicated engine, including child mounts and networking. The Unix socket is a second demonstrated connection method with the same authority; it used a disposable daemon, not the developer's shared OrbStack socket.

An unrelated policy update terminated established Docker and database streams. A no-change control completed all messages. The source analysis identifies a global policy-generation invalidation, not a flaky database. Revocation was tested separately and also closed active connections. Do not hide this behavior with automatic retries or assume that adding a new port is connection-safe.

Executable replacement denial preserves OpenShell's integrity guarantee. Turning that check off would not satisfy the experiment. An upstream capability would need an explicit, auditable way to authorize a rebuilt artifact, or an integration would have to use distinct output identities. Likewise, preserving unaffected connections while still enforcing revocation needs selective revalidation, not removal of the reload guard. Those changes exceed a small experiment patch here. Native companion lifecycle ownership also needs an actual released ownership mechanism or a separately scoped external owner. No controller or daemon manager was developed.

Agent memory and CPU limits are separate from the dedicated engine's aggregate limits. The 64 MiB agent allocation test triggered an OOM kill. The engine and its Docker children shared a separate 2 CPU/4 GiB cap; child-specific caps were checked. These do not form one combined agent/daemon budget. VM CPU/memory configuration is a separate profile.

## Simplest demonstrated approach for Jackin

Build the small pinned Claude/Rust image with Docker; start OpenShell with an explicit role-hook command and tool environment; give ordinary instances no Docker grant. For the selected instance only, attach an approved project volume at the same absolute path in agent and dedicated external engine, then connect with per-instance mTLS and a fixed service-port allowlist. Use an external fixture owner for the engine and its cleanup. Keep policy static while streams run; choose fresh executable output paths after native source changes or run the development test inside Docker.

This demonstrates the mechanics for a conditional prototype. It does **not** supply native daemon ownership, transparent same-path native rebuilds, connection-safe policy updates, reliable forced-client cleanup, inherited child network policy, or authenticated agent operation. Those limitations must remain explicit before Jackin integration work starts.

## Collateral incident

The first gateway configuration temporarily shared the installed gateway's default Docker namespace. Three originally running Docker sandboxes were later found stopped at a common timestamp before final cleanup. Later controlled tests demonstrate namespace interference, but retained logs do not prove who caused those original stops. The unique-label profile remained healthy. This is a material operational hazard and a limitation of the run, not evidence that unrelated workloads were preserved. The original gateway's registered CLI certificate was stale; a temporary owner-API profile authenticated successfully without disabling TLS or editing the original configuration. The user subsequently approved corrective restoration. The original gateway performed guarded stop/start for the exact three IDs; all three are now Ready and pass harmless exec. No original gateway configuration or registered CLI credentials were changed. The initiating stop actor remains unproven. See `results/collateral/gateway-analysis.md`.
