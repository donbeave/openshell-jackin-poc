# Full replacement architecture and decision register

This document defines an architecture candidate covering the full replacement scope, with unresolved decisions and no passed combined integration. It is gated by the candidate comparison and live proofs. Until those gates pass, it is not an approved implementation baseline. No Jackin runtime fallback is retained. Docker may build images and may be OpenShell's compute infrastructure; it may not execute Jackin agent/version/verification workloads directly.

## Capsule decision comes first

Candidate A retains the current trusted Capsule root supervisor, per-account UID drop, peer-authenticated local sockets, child ownership, and host attach protocol under OpenShell. Candidate B moves trusted account/operator/usage/control decisions outside workloads and uses separate sandboxes for two account domains and a separate generic shell domain. Both are evaluated against the same outcome table; successful primitives from different candidates cannot be combined into a pass.

| Required outcome | Candidate A | Candidate B proposed mechanism | Evidence gate |
|---|---|---|---|
| Trusted multi-account isolation | Root Capsule controls UID/GID and sockets | One sandbox/private store per domain; workload helper has no cross-domain authority | A root-setting compatibility and current binary; B two real authenticated accounts + shell denial |
| Persistent multi-session UI | Current Capsule owns PTYs and protocol | Trusted host groups domain session endpoints; domain helper owns only same-domain PTY I/O | Input ownership, session control, exit ownership, disconnect/reconnect, failure tests |
| Host actions | Existing host protocol relay | Same frame types, authenticated desktop client and domain/session binding | Image/export/URL/resize/detach byte replay and wrong-client denial |
| Scoped usage and credential execution | Existing peer-UID scoped relay/approval | Host reuses authorization/approval functions, bound to target/sandbox/domain/admission epoch | Actual channel approval/denial/cancel/timeout/revocation and harmless secret consumer |
| Privilege/child ownership | Root UID switch + Linux/Darwin reaping | Non-root workload process manager with one child owner; host control separate | Root rejection/acceptance; grandchildren/zombie/exit status; Darwin only on macOS host processes |
| Coherent lifecycle/limits/status | One role container plus optional engine | Logical instance groups domains and owned resources; partial states visible | Aggregate budgets and failure after each transition, no phantom success |

Live root-policy creation now rejects UID/GID 0 (`evidence/capsule/a-root-policy.json`), while pinned Capsule isolation requires root before dropping identity. Candidate A therefore fails for its current root-started isolation mechanism; the exact pinned Capsule executable was not run. Candidate B remains unproved beyond separate filesystems and generic PTY reconnect. Candidate B is the proposed design direction because it does not put trusted cross-account authority in an agent-writable process. The new POC proves only isolated filesystems and generic PTY reconnect, not the full Candidate B interface. A final accepted candidate requires the live comparison findings; otherwise this decision remains a readiness blocker.

## Ownership and records

A **target** is one gateway identity, compute driver, endpoint, workspace scope and platform. A **domain** is a set of sessions permitted to share private account data and authority. A logical instance groups its role/project and multiple domains; a shell is always a separate domain from account-bound agents. Two sessions may share a domain only after the same account/workspace/revision admission. They may share approved project data across domains without sharing private homes. Adding a different supported agent builds its own role-derived image and creates a separately admitted domain when its private account authority differs; a logical instance does not assume one image contains every adapter. Domain sandboxes retain their own executed digest/platform.

| Resource/decision | Owner | Identity and authority |
|---|---|---|
| Role admission, workspace/account permission, trust, grants | Trusted Jackin host logic | Role content digest; workspace ID; account revision; admission epoch |
| Image build and builder cache | Docker/Buildx builder, invoked by Jackin image service | Builder endpoint/architecture, recipe key, OCI manifest/platform digest and config ID distinguished |
| Gateway and compute driver | Operator/OpenShell | Target ID, gateway authenticated identity and version/capabilities, isolated state directory and namespace |
| Sandbox/supervisor/process isolation | OpenShell | Target/workspace/canonical unique sandbox name, immutable UUID, observed runtime generation |
| Logical instance | Trusted Jackin state | New random instance ID, role key, target, project ref, desired/current lifecycle, domain and resource receipts |
| Session | Same-domain session I/O helper; trusted host grants control | Instance/domain/session ID, sandbox UUID/generation, controller client lease; no workload-issued global authority |
| Private account state/config | Jackin storage policy; target persistent store | Per-domain store ref/version, staged publication epoch and verified committed account assignment |
| Project data | User/Jackin workspace logic; target storage mechanism | Local canonical path/worktree/clone metadata, or explicit remote replica ID/revision/conflict state |
| Approved credential execution | Trusted Jackin approval/admission logic | One request ID bound to domain/session/consumer/approved command/expiry/revocation epoch |
| Optional engine and children | Proposed OpenShell-compatible capability owner, not old DinD manager | Domain-specific engine resource receipt, boundary, CA/certificate refs, network/volume/child inventory; capability disabled by default |
| Image delivery and target caches | Target delivery adapter/OpenShell stores | Digest/platform and complete-transfer receipt; active/retained instance consumers across every target |
| Host clipboard, URL, export, terminal, keep-awake | Correct desktop client/host service | Authenticated client ID and owning session; no server-side desktop side effects |

Proposed records (new format; no legacy import):

- `TargetRecord`: ID, endpoint, gateway identity, driver, platform, workspace scope, auth reference, owner namespace, storage class, VM size class, capabilities and protocol version.
- `InstanceRecord`: instance ID, role/revision, target ID, project store reference, role content/recipe identity and per-domain agent image digest/platform map, desired/observed state, domain refs, resource receipts, last complete inventory revision, preservation state.
- `DomainRecord`: random domain ID, kind (account/shell/worker), admitted workspace/account/revision/epoch, private-store ref, sandbox ref and session refs. Shell/worker carry no agent account.
- `SandboxRef`: target ID, workspace, never-reused canonical name, immutable sandbox UUID, observed runtime generation, image digest and spec hash.
- `SessionRef`: domain/session ID, sandbox generation, session protocol version, PTY/process identity, observed exit, input-owner desktop client/lease. Process exit is recorded once by its owning supervisor.
- `OwnershipReceipt`: intent ID, stable request ID, owner instance/domain, exact resource identity and target scope, transition, cleanup state and retained references; persisted before an effect that can leave a resource behind.
- `RetainedStateRef`: project/private store ID, committed epoch, flush/capture outcome, image digest needed for recreation, holds, dirty/unpushed/unknown flags. Unknown state preserves data.

Approved credential consumer placement: the command that needs the secret runs only in the admitted account domain sandbox under its untrusted account UID. The trusted host approves a literal command/request and publishes a one-use response through the authenticated domain-bound exec channel; it never gives the helper account-catalog or operator authority. The secret is visible to that approved consumer and can be disclosed by it. Existing MCP request/approval/result protocol is retained; remote one-use delivery, cancellation/timeout/revocation and intended MCP response remain NOT TESTED. A fresh unrelated credential-execution sandbox would change account/session semantics and is not silently substituted.

These are conceptual interfaces/records, not production implementations.

## Narrow interfaces replace Docker assumptions

`ImageBuilder` prepares a digest-bound role+selected-agent image using Docker/Buildx. `ImageDelivery` verifies presence/import/pull by platform digest on each target. `SandboxControl` creates/gets/lists/starts/stops/deletes scoped resources with typed unavailable/unauthorized/absent/incomplete states and confirmed asynchronous deletion. `SessionTransport` carries exact argv and byte streams/PTY resize/signals/exit plus detach/reconnect. `DomainAdmission` reuses account/workspace policy; `ProjectStore` separates local host mounts from remote replicas; `CapabilityLease` requests explicit managed Docker and owns its resources. None mirrors all `DockerApi` methods.

Long-term Rust route proposed: generated clients from the pinned gateway protobuf types with an authenticated tonic channel. Local mTLS uses private CA verification, hostname verification and client identity; remote mode selected for qualification is operator-issued mTLS over reachable authenticated endpoints, keeping credentials independent per target. OIDC may be an additional supported mode only after renewal/failure tests. The released CLI adapter is a small POC route, not proof that the custom Rust channel, stable request IDs, streaming/cancellation, or renewal works. OpenShell main's SDK mTLS addition cannot be silently imported into the stable result.

Transport requirements: literal argv without shell concatenation, independent stdout/stderr/exit, binary stdin including NUL, bounded slow receiver queues/output, explicit cancellation semantics, remote exit observation independent of local CLI exit. Diagnostics go to stderr, never protocol stdout. Connection loss leaves state unknown until re-observed; no invented automatic process-kill guarantee. Application readiness waits for the versioned session handshake after OpenShell runtime readiness.

## Safe identity and retries

Gateway mutation APIs at the reviewed pin use canonical names; DeleteSandbox has no immutable-UUID precondition. A read UUID followed by a name action is not atomic. Proposed safe strategy: Jackin owns a dedicated authenticated namespace/workspace; every sandbox canonical name includes a fresh random generation and is never reused, including retries and recreate. One trusted Jackin host owns allocation for a logical instance and serializes it in its ownership journal; multiple desktop clients do not become independent allocators. General multi-host collaboration remains future scope; workloads cannot create/rename/delete or receive gateway credentials. Other gateway administrators must honor namespace ownership; a malicious administrator is outside the authority assumption. If independent actors may reuse names in that namespace, require a server-side UUID precondition before this strategy is accepted.

Use one stable create/stop/delete request UUID per intent. Persist it before first RPC; replay within server's advertised retention window only. After unknown/lost response inspect full authorized scope and reconcile ownership; do not issue a fresh create blindly. Beyond retention window, exact scoped identity/state reconciliation is mandatory. Test duplicate requests, conflicting payload, lost response, version mismatch, same-name replacement and unauthorized/outage cases.

Interpret the actual DeleteSandbox response: `DELETION_OUTCOME_ACCEPTED` is admission, not completion; `DELETION_OUTCOME_COMPLETED` carries the captured immutable `sandbox_id` but its protobuf contract explicitly permits downstream platform garbage collection still finishing. The reviewed proto exposes those fields, and compute/mod.rs:2848-2974 checks the captured UUID before removing its deleting record. The CLI fixture observed pending cleanup, so the typed completion route and final downstream cleanup both need live testing. Gateway-record completion cannot be presented as proof that all platform children, volumes or mounts are gone. Poll only the expected authenticated workspace and reconcile the original UUID/owned receipts; generic name absence alone is not a completion receipt. The reviewed `grpc/sandbox.rs:1700-1715` explicitly maps a delete workspace PermissionDenied to NOT_FOUND. This is source evidence, not a live unauthorized-scope test. A generic NOT_FOUND could indicate wrong workspace or authorization; it never permits retained host-data purge. Purge also needs owner authorization, full inventory validity, no hold and explicit retained-data decision. Builder images/target image caches/foreign resources are separate objects.

## Image recipe and hooks

Retain existing role discovery/trust, adapter install logic and recipe rendering. Recipe identity must cover: role commit/content, Dockerfile and full context including hooks/config, base digest/platform, selected agent/version/install source, fallback path, generated configuration/plugin sources and pinned versions, Capsule/session-helper content/protocol, renderer version, build arguments and toolchain. Secret contents are not placed in cache labels; a secret-dependent installation needs an explicit non-secret revision input and protected build mechanism. Actual Architect currently includes dynamic external skill/marketplace sources; resolve and record their revisions before claiming a reproducible key.

Build with Docker/Buildx during launch, then verify recorded metadata against executed digest. Unknown agent version is discovered from trusted build metadata or OpenShell execution, never `docker run`. Cold preparation, valid cache reuse, forced rebuild and role/version changes have different evidence samples. Gateway controls entrypoint: start an explicit small bootstrap that applies role hooks in the required order and then the domain's agent/session entrypoint. Do not assume image ENTRYPOINT runs. Hooks run in that domain's identity/private configuration, not with cross-account operator authority.

Same-engine local presence is not image delivery. Remote/Kubernetes use an authenticated registry with digest/platform verification and pull credentials scoped to target. VM uses documented import/rootfs preparation pinned to the same image, with digest provenance. Interrupted publication is incomplete and not adoptable. Retained instances pin required image/store references for ordinary recreation. Builder cache prune and target cache prune each account for active and retained consumers.

## Storage and targets

Local container targets use operator-approved project and per-domain private volumes, retaining resource admission. A volume backed by a host bind is still host exposure and must be admitted only after canonical-path/ownership checks; approval labels alone do not prove a security boundary. Direct host binds require the documented admission relaxation and therefore are not silently chosen. The actual live-host mechanism needs proof of RO, ownership/watch/Git links/symlinks/concurrency on each engine. Project sharing does not share private account data.

VM targets use distinct gateway/state/auth configurations per driver and size class (gateway `vcpus`/`mem_mib`, not ignored per-sandbox flags). Directory-only virtiofs mounts and three x86_64/32 ARM64 limits constrain layout. Use one authorized project directory plus one private domain directory and an explicit metadata directory if needed; never broaden a private parent mount to reduce count. A worktree's auxiliary Git metadata must fit without exposing unrelated repositories. Otherwise fail admission with actionable layout diagnostics. Virtiofs permissions, callbacks and filesystem limitations remain qualification gates.

Remote target project model is a target-local durable replica. Before launch publish a pinned baseline; host edits/agent edits are synchronized only at explicit boundaries until a tested live synchronizer exists. Export compares base/host/remote hashes and refuses conflicting overwrite; preserve both sides for user resolution. Remote Worktree/Clone retain Git identities on target with source/base revisions. This model changes live Shared behavior, so remote Shared requires a proven synchronization mechanism or an explicitly documented new remote workflow; it is an unresolved capability, not presumed parity.

Kubernetes needs a qualified controller/CNI NetworkPolicy enforcement, authenticated gateway, namespace/PVC ownership and imagePullSecrets. No row passes from Helm YAML or source alone. Target outage must not hide other targets. All desktop actions return to the initiating authorized client, never gateway host. The transport envelope binds target/sandbox generation/domain/session/client/request ID around reusable host protocol frames. Losing or replacing that client cancels an in-progress export/clipboard/open request; it is not delivered to a newly attached client without a new authorization. Current frames alone do not prove this distributed routing.

Durability: writable container layers are disposable. Durable project/private stores survive stop and normal recreation. Stop is not pause, and completed stop does not imply every VM flush succeeded. Flush/export failures surface as uncertain retained state; preserve store/image references and prevent destructive cleanup. Test orderly and interrupted shutdown, store publication interruption, dirty/unpushed work and failed session inspection.

## Policy, limits and optional Docker

Retain role/workspace/CLI profile/grant precedence and requested effective restrictions. Locked: allowlist/no Docker/agent identity/no sudo/4 GB/2 CPU/512 PIDs; hardened: allowlist/no Docker/16 GB/4 CPU/2048; standard: network open/no Docker/16 GB/4 CPU/2048; compat: open/explicit privileged Docker/sudo/unbounded in current source. These are source-derived baseline calculations, not verified OpenShell guarantees. An unsupported restriction fails launch; no ineffective profile label is retained as enforcement. Provisioned sudoers does not justify root in agent sessions.

Domain splitting adds separate workloads/supervisors. Admission can reserve portions of an instance budget, but reservation alone is not an enforced aggregate cgroup limit. Define resource grants per domain plus explicit aggregate admission; if a hard instance-wide runtime cap is required, prove an OpenShell-supported parent boundary or upstream change. Gateway-level PID limits may require worker/profile target classes. CPU/memory/PID/temp/nofile/network/filesystem and privilege enforcement all need denied and allowed operations.

Retain changed-executable integrity failures. Repeated ordinary Cargo/nextest/Testcontainers loops must pass at the same output path under the intended profile before the replacement is viable. Fresh output paths and child-container loopback tests are workarounds, not transparent solutions. Static policies avoid promising uninterrupted arbitrary policy updates; credential/provider configuration changes must still be tested for connection interruption and explicit recovery.

Optional Docker comparison:

| Mechanism | Owner/boundary | Current conclusion |
|---|---|---|
| Daemon inside OpenShell-managed compute | Sandbox owns daemon/children; requires namespace/capability/runtime support | Prior rootless iptables failure; no released compatible complete path proved |
| OpenShell-managed companion | Gateway-owned engine with explicit parent/child lifetime and private service | No executed released ownership operation found; proposal only |
| Small extension | Gateway invokes an explicit owned capability lease with exact cleanup receipts | Could be upstream work; no pinned diff/run. Size is unresolved, cannot call small without design/proof |
| Disposable external engine forwarding | External fixture owns daemon/children/network/volumes/TLS | Prior mTLS/Docker/Compose/Testcontainers pass within limits; does not prove managed OpenShell-only capability |

Public issue research is retained in `evidence/versions/openshell-docker-issue-113*.json` and `openshell-docker-search.json`. [Issue #113](https://github.com/NVIDIA/OpenShell/issues/113) describes candidate daemon approaches but its closed state is not released support or execution evidence. [Issue #2676](https://github.com/NVIDIA/OpenShell/issues/2676) reports private-registry pull authentication failure on an older development build; this is a reason to test stable authenticated delivery, not a new stable execution result. The complete architecture requires a managed capability and has no selected tested implementation yet. Reusing old Jackin DinD runtime manager would be a deviation from this scope, so it is not the chosen substitute. Default domain receives no Docker endpoint/socket/engine credentials. Enabled capability needs a separate engine per authorized domain, never shared across private-account or shell domains. Its receipt is keyed by target/instance/domain; logical-instance teardown aggregates these engines without merging their authority. Project storage may be shared, private homes are never attached to an engine. It also needs engine and child location/resource/network receipts, project path mapping, concurrent unmodified project tests, online pulls, Buildx/Compose/ports/callbacks, cross-instance denial, stop/restart/teardown/interrupted provisioning. Child traffic does not inherit agent policy in the external fixture; engine/children need their own tested boundary. Cleanup after killed tests is explicit eventual owned-resource cleanup, not an invented immediate guarantee.

## Verification worker

Keep policy freeze, candidate/check hashes, independent review and result recording in trusted `jackin-workflow`. Replace only execution with a fresh account-free OpenShell sandbox. Preserve current pinned Python image, exact argv, RO candidate and separately RO trusted bundle, no network, read-only root, 512 MiB/1 CPU/64 PIDs, bounded `/tmp` 64 MiB noexec/nosuid and `/build` 256 MiB, 64 KiB per output stream and 1–3600 s policy deadline. Root UID is not required product behavior. The current wrapper kills the process group and observes exit; replacement must prove actual remote group termination, including client/control loss, before recording a result.

The live v0.1.5 worker fixture now reproduces a blocking incompatibility: the existing Python wrapper receives `PermissionError` from `os.killpg`, and its child survives. Pinned `openshell-sandbox/src/linux/process_signal.rs:20-35` deliberately denies group/broadcast signals; this source explanation is separate from the live result. A trusted sandbox-level termination route must be tested for actual child cleanup and exit observation, or an upstream safe ownership-aware signal operation is needed. Do not simply allow every negative PID. The executed fixture used direct host binds with resource admission disabled and `ReadonlyRootfs=false`; it does not qualify the proposed admitted storage or literal read-only root. See `evidence/verification/timeout-process-group.json` and control fixture report.

OpenShell sandbox application readiness is distinct from test completion. Record candidate commit/tree, policy/check bundle/image digests, sandbox UUID/generation, exact command, observed exit and cleanup outcome. Timeout and unavailable are not test failure exit codes. Worker gets no agent state or credentials. No host/direct Docker fallback. If read-only root/PID/tmpfs/output/time semantics are unavailable, an upstream capability or tested configuration is required; do not weaken the worker.

## Lifecycle and subsystem actions

New state machine: Planned, Building, ImagePrepared, StoragePrepared, DomainCreating, RuntimeReady, ApplicationReady, Active, Stopping, Retained, Deleting, Absent, CleanupPending, Failed, Unknown. Target availability is independent of desired/observed instance state. Persist ownership intent before external create; record actual IDs before moving forward. Partial initial required-domain startup does not make a logical instance ready. Adding a later domain may fail while existing domains remain Active; expose Degraded plus each domain state and pending request, rather than destroy working sessions or hide a failed sibling. Aggregate limits and lifecycle enumerate all domain sandbox and capability receipts. Reverse cleanup of owned ephemeral resources preserves committed stores. Missing/unauthorized/outage are distinct and never converted into host deletion.

`hardline` attaches or reconstructs retained state; `eject`/`exile` remove runtime/capability resources while preserving required retained state; `purge` is separately destructive after confirmed authorized absence/guards. Prune uses all targets and retained image references. Prewarm builds images and optionally prepares explicitly requested capability, never silently grants Docker. Prepared resource adoption is a single ownership transfer; mount drift/revision mismatch rejects adoption.

|---|---|---|
| Roles, admission, Git materialization, workflow policy/results | Retain product logic | Pure decisions do not need a runtime rewrite; new storage/transport qualification still required |
| Capsule UI/protocol types | Retain product logic / replace transport | Preserve UX; root trusted process structure cannot be assumed under non-root OpenShell |
| Account/private state and identity | Replace storage or identity mechanism | Sandbox domain replaces local peer-UID as cross-target identity; reuse authorization decisions |
| Role/version/worker execution | Replace execution through OpenShell | Eliminate direct Docker and Apple workload execution |
| Host authority/session grouping | Add a small Jackin mechanism | Domain/session/desktop-bound grants and receipts; production broker/multiplexer excluded from research |

| Managed Docker, unsupported limits/identity preconditions if needed | Require an OpenShell change | No tested released solution selected; exact upstream work is a blocker |
| Builder and explicit Docker tooling | Retain narrowly scoped operations | Allowed image build/capability/infrastructure only; see refactor deletion/retention ledger |
