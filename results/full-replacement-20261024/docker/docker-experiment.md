# Dedicated Docker / Compose / Testcontainers evidence (macOS ARM64)

Scope: this directory's Docker client and optional Docker engine experiments only. OpenShell version 0.1.5; gateway `jfr-20261024-d` on `https://localhost:28610`, Docker compute driver v0.1.5, OpenShell source pin `bdb956f2cd65a635f1294fccf1d138d263bf650f`. Host was macOS ARM64 with OrbStack. Docker client 29.9.2, default engine 29.8.2. The dedicated engine is separate from that default engine.

## Engine ownership and credentials

A and B are external disposable DinD fixtures, not OpenShell-owned engines:

- B outer container ID `ec449dfdada098f2831f8d38ce9459d725e182e913e50476d4722f530ed6660c`, image `docker:29.8.2-dind@sha256:1e08cdb63405ca788aea94ef35b792d1e299607c667d33d7bcbcae1fd2611ced`. Its API is bound only to `127.0.0.1:28481`; B engine ID `253d0666-9d55-4dc5-b165-733d2eb778e4`; Docker root `/var/lib/docker`.
- B engine data volume `jfr24-docker-b-data`; workspace volume `jfr24-dk-host-project` (owner label `followup-docker-engine`, attachable workspace `default`, host source is this experiment's `results/.../docker/host-source`). The engine outer container also has the project volume at `/workspace/rust-project`, allowing exact absolute-path child binds.
- Client and server certificates live under ignored `experiments/.../docker/private-b/`. A and B have distinct CAs and client certs. Host client certs are staged in sandbox home (`/home/agent/.docker/client/client`) only for these test sandboxes. No values are saved in result files.
- A client certificate sent to B fails TLS with `tls: client didn't provide a certificate`; B's identity succeeds. This confirms TLS client identity isolation. External fixture script/host owns and removes the daemon container, its data volume, certificates, ports, project volume, and child resources. Stopping/restarting an OpenShell sandbox did not stop the daemon. After sandbox stop, a host-side mTLS query still reported B and its Redis/nginx images; after start the sandbox read its project marker and reconnected to the same engine ID.
- Therefore this demonstrates **external daemon connectivity**, not OpenShell companion-engine ownership. Manual fixture cleanup is not OpenShell cleanup.

## Rootless Docker in workload attempt

One ordinary-restriction attempt with official `docker:29.8.2-dind-rootless@sha256:c652fa9cebdaa3d655c33c6389c3c409f9a0fea6449c7d7c56c486fe71af0591` did not yield a daemon-ready sandbox. Initial policy omitted read-only `/bin` and `/sbin`; OpenShell rejected spawning the shebang entrypoint with `Permission denied (os error 13)`. A second sandbox added only those read-only interpreter paths, no privileges/capabilities/writable paths, and launched `/usr/local/bin/dockerd-entrypoint.sh`; its main process exited status 1 before readiness. OpenShell's captured logs do not contain daemon stderr. Result: **BLOCKED** as rootless daemon evidence, not a general incompatibility claim. No further startup attempts or security weakening. See `managed-engine-research.md` and `rootless-*` evidence.

## Managed-engine conclusion

This experiment proves external mTLS daemon connectivity and useful Docker/Compose/Testcontainers operations. It does not prove OpenShell-owned companion engines. The v0.1.5 documented driver interface does not expose per-sandbox engine provisioning, durable ownership, recovery, and deletion. Rootless startup remains unresolved. A full replacement therefore needs a new OpenShell companion lifecycle capability or a product-approved owner outside OpenShell; the latter conflicts with the requested OpenShell-only execution design. Do not report external forwarding as managed support.
