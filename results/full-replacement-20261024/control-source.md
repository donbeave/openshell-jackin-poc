## Jackin control ownership

Jackin owns the user-facing console, role/workspace/account decisions, and Capsule session protocol. OpenShell can supply sandbox process execution and basic sandbox lifecycle. It does not replace the Capsule multiplexing/control protocol or Jackin's state machine. The pinned source has separate Capsule daemon and client paths: `crates/apps/jackin-capsule/src/main.rs:21-51`; daemon selection treats PID 1 or `JACKIN_CAPSULE_FORCE_DAEMON` plus a daemon entrypoint as daemon, while recognized client subcommands route through `run_client_mode` (`crates/apps/jackin-capsule/src/argv.rs:16-44`). Therefore the forced-daemon variable must be scoped to the daemon process. `status`, `snapshot`, `send`, `events`, `usage`, `agents`, and `attach-proxy` are client commands and must never accidentally launch another daemon.

The host attach path first tries a direct Unix socket; missing, overlong, or non-negotiating socket falls back to `docker exec -i <immutable-container-id> <capsule> attach-proxy` (`crates/services/jackin-runtime-attach-transport/src/transport.rs:12-34,38-70`). This fallback relies on runtime-specific exec and stable container identity. An OpenShell rewrite needs an equivalent binary-safe bidirectional transport to Capsule. Tested OpenShell shell/PTY behavior is not a Capsule protocol test.

Capsule's required product protocol includes negotiation; session create/focus/send/snapshot/status/events; exclusive operator control; terminal input/output, resize and interrupt; reconnect; and file/clipboard/URL/reveal-path and activity/usage messages. Capsule implementation surfaces are `crates/apps/jackin-capsule/src/client.rs`, `src/client/session_cmds.rs`, `src/client/status.rs`, `src/daemon/control/`, `src/daemon/session_events.rs`, `src/daemon/session_lifecycle/`, `src/clipboard.rs`, and `crates/services/jackin-runtime-session-control/`. Its own source/tests show this protocol is Jackin-owned. Required tests must check message origin and authorization before host actions; a transport-only pass is insufficient. Client disconnect, agent/session exit, sandbox stop/restart, and conversation resume are distinct transitions.

The current Docker path owns immutable container IDs in the instance manifest and refuses destructive cleanup if role/DinD identity mismatches (`crates/services/jackin-runtime/src/runtime/cleanup/eject.rs:53-76`). This identity guarantee cannot be reduced to a read-by-name followed by a name-based mutation. OpenShell Rust SDK deletion returns `sandbox_id`; `wait_deleted` accepts that ID to avoid waiting on a same-name replacement, but source does not establish atomic name-to-ID mutation guards (`results/rewrite-readiness/sources/openshell-rust-sdk-client.rs`, SDK docs at `results/rewrite-readiness/sources/openshell-rust-sdk-readme.md`). The required stale-target experiment remains open.

The SDK source initializes create/stop/start/delete RPC `request_id` fields to an empty string in the curated methods (`results/rewrite-readiness/sources/openshell-rust-sdk-client.rs`, create around lines 139-147, delete 355-364, stop/start 374-397). No evidence here establishes retry idempotency, a client-supplied request ID, or exactly-once execution. A timed-out create/exec therefore has an uncertain outcome. Required test uses same request ID on retry, writes one marker, and verifies no duplicate command; if the released API cannot express this, report an upstream API blocker. Never replay an agent prompt to hide uncertainty.

## OpenShell control surface and transport evidence

OpenShell v0.1.5 Rust SDK offers curated create/get/list/delete/wait/exec and, in current SDK source, stop/start. It offers raw generated gRPC for remaining RPCs. Curated exec is non-streaming and `tty: false`; it does not establish Capsule full-duplex transport. Rust SDK `ClientConfig` supports plaintext, server-authenticated TLS/private CA, OIDC bearer and Cloudflare tunnel, but **not mTLS client identity** (`results/rewrite-readiness/sources/openshell-rust-sdk-readme.md`; `openshell-rust-sdk-config.rs`; `openshell-rust-sdk-transport.rs`). Its `insecure_skip_verify` option must remain false. The CLI has a separately implemented legacy mTLS path; prior gateway evidence ran `openshell ... -o json` successfully with verification on (`results/gateway/evidence.md:17-56`). CLI execution is a candidate only after proving exact v0.1.5 machine-readable output for required operations, argument boundaries, correct gateway identity/config isolation, errors, and stream semantics. Human-readable parsing is unacceptable.

Prior Python SDK execution did prove create, wait-ready, exec, inspect/get, stop/start, delete, and wait-deleted on the historical OrbStack Docker profile (`results/repeat/sdk-lifecycle.json`). It does not prove Rust caller compatibility or full-replacement lifecycle semantics. Existing PTY experiment covers a terminal primitive, not the Capsule bridge (`CAPABILITY_MATRIX.md` B1-B5). No prior execution covers lost responses, same-request retry, stale name reuse, generation protection, event recovery, two gateways with duplicate display names, or full Capsule session boundary behavior. These are **NOT TESTED** for the rewrite.

Potential small Rust control client: pin `openshell-sdk` to v0.1.5, exercise server CA and hostname checks first, then explicitly probe mTLS. Since the released Rust SDK has no client cert option, do not fall back to insecure TLS. Either (a) securely invoke the release-matched CLI with isolated per-gateway config and machine-readable output after proving the CLI contract, or (b) propose a narrow upstream Rust SDK mTLS transport capability and test it on a separate experimental branch only after unmodified release failure. Keep raw gRPC calls limited to capabilities absent from curated methods. Neither route replaces Capsule.

## Observability, events, and target matrix implications

Jackin diagnostics and usage/event handling are separate from OpenShell runtime state. Active Capsule has session activity, state and exit events; `crates/apps/jackin-capsule/src/daemon/session_events.rs:15-69` updates visible state and publishes exit events. Usage relay is an active capsule path, whereas account-usage host authority and signed credential transcript v2 remain inactive foundations at this pin (`results/rewrite-readiness/product-contract.md:87-97`). Replacement needs event origin/instance attribution, event interruption followed by a fresh status query, and separate deterministic activity/usage transport tests. A transport test does not prove correct provider billing.

## Smallest decisive control experiments

1. On unmodified pinned v0.1.5, run one Rust client against a fresh isolated mTLS gateway: valid CA/hostname/client identity succeeds; wrong CA, hostname, missing client identity, and wrong client identity fail. Keep TLS verification enabled. Record gateway target identity and credentials separately.
2. Use released CLI JSON or Rust SDK only. For each API operation preserve status, stdout, stderr; exec argv containing spaces, quotes and metacharacters must stay literal. Confirm raw bytes never mix with diagnostics.
3. Exercise create, list, inspect, exec, stop, start, deletion confirmation; recover by immutable ID. Inject lost create/exec response; repeat same request ID and prove one marker. If API cannot take request ID, record the missing guarantee.
4. Execute unchanged Capsule as root at the real PID1 path, create two separate identities/homes, inspect UID/GID/groups/capabilities/filesystem; then attach, focus, send, snapshot, status, events, exclusive control, interrupt one while other remains active; NUL/split/backpressure/EOF/PTY resize/disconnect/reconnect; export, clipboard, URL/reveal, activity and usage auth. Scope forced-daemon env to daemon only and prove client commands do not daemonize.
5. Stop/start, delete/recreate, inject process/gateway/client interruptions, and stale-name reuse. Verify retained state, runtime resources, two-gateway isolation, fresh-query event recovery, and explicit error when retained state is absent. Eject/exile retains state; purge first requires all owned resources absent.
6. Repeat only the complete accepted journey across each required target. Unavailable target is BLOCKED/NOT TESTED, not extrapolated.
