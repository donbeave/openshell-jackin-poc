# OpenShell Docker tmpfs and verification-worker follow-up

**Worker result: FAIL for the required read-only-root worker contract.**

**Tmpfs patch result: PASS for the narrow Docker option-translation behavior only; mechanism EXPERIMENTAL PATCH.** OpenShell v0.1.5's released Docker structured-mount path rejected `nosuid` on the tested OrbStack engine. Docker's same-engine create-only control accepted the exact options through `HostConfig.Tmpfs`. The separate patch routes validated tmpfs options to that field and preserves the supervisor CA tmpfs. Patched sandboxes started with `/tmp` and `/build` as actual tmpfs mounts, retained `noexec`/`nosuid`, passed a functional `/tmp` noexec denial, passed both tmpfs exhaustion checks, and retained the required volume-admission/protected-target denials.

The worker journey did not satisfy its full security contract. P10 showed the Docker root mount remains writable (`ReadonlyRootfs:false`) and writing in the image-declared writable `/work/repo` succeeds. P11 denied that workdir write with its configured Landlock policy. P14 tested whether that selected policy supplies the required boundary: after ordinary create, mkdir, data-write, truncate, and rename attempts were denied, `chmod` on a UID-1000-owned file under `/home` succeeded. This is a decisive FAIL for the selected read-only-root equivalence. It does not establish that a physical `ReadonlyRootfs:true` flag is the only possible solution. No change was made to the tmpfs patch to address filesystem policy.

## Reproduction

From the repository root:

1. Check out OpenShell at `bdb956f2cd65a635f1294fccf1d138d263bf650f` and apply the exported patch: `git apply results/full-refactor-20261024/verification-worker/patch-tmpfs/tmpfs-patch-final.diff`. The tested experimental branch is pinned at commit `68cfa648538a497acd4af2cf48424eda9834ba0f`.
2. Build the patched gateway from that worktree through its committed `mise.toml`/`mbx` setup: `mise exec -- cargo build -p openshell-gateway`.
3. Generate fresh task-scoped credentials/config with `experiments/full-refactor-20261024/verification-worker/patch-tmpfs/gateway/setup.sh`, then run the patched gateway with `.../gateway/run.sh`; its isolated config points to port 28631. The credentials used in the saved run were removed during cleanup.
4. Build the exact P10/P11 fixture image from the corresponding Dockerfile in `experiments/full-refactor-20261024/verification-worker/patch-tmpfs/`.
5. Run the worker client using `capture-worker.sh <unique-name> <image-tag>`; the script stores stdout, stderr, exit status, filtered Docker config and workload logs.

The patch's focused test command was `mise exec -- cargo test -p openshell-driver-docker`; exit 0, 150 passed, 2 ignored. The patched gateway build exited 0. Its original binary was deleted from the shared mbx target cache before a hash was captured; the historical tested binary SHA256 is NOT CAPTURED. A subsequent same-commit rebuild exited 0 and hashed `5bb214fdbc41e9035bdd523a0b8686c376b1e00594a8c95f948d1f01d982d1b8`; this is explicitly a rebuilt-only identity and does not replace the missing historical runtime hash. See `gateway-binary-identity.md`. P10–P14 worker evidence does not meet the required contract; P13 recorded sandbox loss after OOM. P12 returned 247 and remained Ready; P13 returned 74 and moved the sandbox to Error after an OOM event. Mapping an uncertain/killed worker result to an explicit infrastructure failure is a proposed product behavior, not implemented or tested. The OOM watcher only observed the OpenShell-created container; it did not run worker commands. Docker stats polling did not sample the transient peak reliably, so no peak-memory number is claimed. The complete raw request/response documents and command outputs are retained; no released failure was overwritten.

## Remaining required upstream capability

The selected P11 policy does not deny all filesystem mutations outside `/tmp` and `/build`; P14 chmod succeeded on a DAC-writable file in `/home`, so the required worker contract remains FAIL. The minimum upstream capability to evaluate is a supported strict workload filesystem policy that denies content and metadata mutation outside explicitly granted writable paths while retaining supervisor operation and volume-admission checks. This may use a read-only root plus tmpfs or an equivalent complete kernel policy; this experiment does not choose between them. No third patch or filesystem subsystem was attempted. OOM fate also needs a deterministic runtime outcome or explicit unknown-result contract; that mapping is only proposed.
