# Independent authority, storage, and cleanup review

Review scope: assess whether the current candidate architecture preserves Jackin's user and security boundaries. This is an architecture/security review of source maps and recorded experiments, not a new runtime execution. Source snapshot is Jackin `6e266406b49da2ab3c55355f3b7d33d1643ee6cd`; the prior runtime experiment group uses Jackin `41bad147b5ba9db09be99b07248531ce1bd867be`. OpenShell release under test is v0.1.5, `bdb956f2cd65a635f1294fccf1d138d263bf650f`.

## Decision

**The candidate is not yet a coherent, proven full-replacement architecture.** The local host-workspace route is a viable *conditional design primitive*: an administrator/Jackin-controlled host creates a labeled Docker local-driver volume that binds one canonical authorized checkout, then OpenShell attaches it with resource admission enabled. This preserves live host bytes without disabling admission. It does not make host storage OpenShell-owned, and it does not prove safe authorization or cleanup in a Jackin product path.

The control client now has strong released mTLS and stream primitive evidence, but the API's name-based mutation behavior violates stale-target safety. The Rust repeat reproduced an old `StopSandbox` request stopping a same-name replacement. Separate historical control evidence reproduced stale `DeleteSandbox` deleting a same-name replacement. At-most-once request IDs do not bind an operation to the resource generation it was created for. A name lock is only a possible mitigation if it fences every delayed request, survives client/gateway restart, and is itself owned durably; that subsystem is not proven. Prefer an upstream immutable-ID/generation precondition on stop/start/delete and re-run the positive and negative tests. Do not call this a harmless cleanup limitation.

The external mTLS Docker fixture is not enough for Jackin's new requirement that optional Docker be managed as part of the OpenShell-only execution design. It proves Docker API connectivity and some child workflows, but not an owner-integrated lifecycle, provisioning, recovery, or teardown contract. Keep the engine manager as a required Jackin-side component behind OpenShell sandbox authorization, with explicit ownership and lifecycle evidence; do not silently reuse the old DinD manager without proving its assumptions against OpenShell identities and resource ownership.

The unchanged Capsule root/isolation route and Candidate B alternative are both unresolved. Root Capsule policy admission was rejected; compilation evidence is not a session test. Ordinary exec and PTY evidence does not prove Capsule's protocol, per-account process isolation, session persistence, host-action authorization, or reconnect semantics. Candidate B is a proposed trusted host-control/account service plus separate shell sessions, not an executed substitute. Do not infer interactive-agent `sudo` from a sudoers file, configuration value, or grant readback; prove a real allowed operation and a prohibited escalation while preserving NNP and profile behavior.

## Workspace authority and volume boundary

Recorded positive probes in `results/full-replacement-20261024/workspace/official-volume-probes.json` and the fresh repeat in `results/full-replacement-20261024/repeat/repeat-result.json` show:

- Direct `type=bind` admission fails with resource admission enabled (`no trusted label resolver`). Keep that failure as FAIL for raw binds.
- A separately created `local` volume with `type=none,o=bind,device=<host path>`, attachable and exact workspace labels, attaches under the configured Docker driver and exposes live host edits and sandbox edits. Atomic host replacement, file watching, working directory, read-only enforcement, permissions and a sibling symlink canary were exercised on the local macOS ARM64 + OrbStack Linux ARM64 path.
- A volume labeled for another workspace is rejected. Admission remained enabled. The positive result therefore depends on an external trusted creator; the labels alone do not prove that the device path is authorized.

The design must keep the trusted Jackin host as source-authority owner: resolve the checkout with strict canonicalization; reject path escape and wrong workspace; inspect exact driver/options/device and ownership labels; ensure the source identity cannot be swapped between validation and use; create/attach/remove only its own uniquely named resources. Existing `validate-volume-source.py` checks the canonical `device` and labels at one point in time, but separate inspect and attach are vulnerable to a race if another actor can mutate/remove/recreate the named volume. Docker authority is effectively host-level authority. The workspace user or agent must not receive volume create/relabel or raw Docker host-builder credentials. The test did not prove protection against a concurrent replacement, directory/symlink retarget after validation, hard links, bind propagation, or host filesystem privacy; do not claim those boundaries.

The symlink test establishes that an unmounted sibling canary was not visible through the mounted source path in that setup. It is not general filesystem confinement evidence. Mount permissions and `/workspace` filesystem policy are both part of the effective boundary. The current probe explicitly added `/workspace` read-write permission; this must be an intentional profile mapping, not a broad policy workaround. The local volume is an **external fixture** owned by the trusted Jackin host/engine, not OpenShell-native storage. Raw bind denial and VM-host share failure remain applicable blockers for their profiles.

## Resource ownership and cleanup

The owner split is viable only if it is explicit in a Jackin resource ledger. For every instance, persist immutable gateway identity, sandbox ID and generation, workspace ID/source identity, image digest, account revision, session state, and—when granted—engine ID, data directory, CA/client identity, network, port leases, volumes, and child resource ownership. Runtime stop must retain the user's project/account state; eject/exile/purge must retain their distinct semantics. A deleted sandbox is not proof that retained files or engine children were removed.

Observed sandbox delete/cleanup confirms sandbox inventory removal in a few fixtures. It does not demonstrate complete product cleanup. Docker's volume names have no separate immutable ID in the recorded inspection, so cleanup must validate fixture/Jackin labels plus exact options/device immediately before deletion and must not use display name alone. The host process owns the source checkout and exported bytes; the dedicated engine owner must remove engine data and child resources according to the explicit command semantics. OpenShell deleting its sandbox must not be described as removing external daemon resources. Conversely, retained state must not disappear when an engine is removed.

Interrupt recovery remains a material gap: a host process can die after volume/engine creation but before sandbox readiness, or after sandbox creation before recording its returned ID. The owner needs a durable intent/resource manifest written before side effects, followed by exact-ID reconciliation. Same-name OpenShell operations are unsafe under delayed delivery until stale-target protection exists. Cleanup retries may be idempotent only after ownership and identity are checked; do not blindly replay stale name-based delete. The present evidence does not establish recovery across a lost create reply, a lost execution reply with output recovery, or two gateways with independent namespaces.

## Identity, host actions, accounts, and inventory

Rust Tonic `from_parts` with verified server CA, hostname and client identity is a tested released control-transport primitive on local and one Linux endpoint. It does not establish Jackin account authorization. An alternate subject signed by the same trusted CA was accepted by the tested gateway, so the CA is the present trust authority; OU/CN should not be treated as a role boundary without an explicit authorization check. Per-account model/API-key, profile-sync and OAuth paths remain separate. Current source maps and earlier status mark live authenticated tasks blocked/unavailable; harmless account fixtures prove neither provider login nor credential redaction in real agent execution.

Jackin host actions require a separate authenticated origin. Clipboard, URL-open and reveal-path requests must be bound to a session/account and approved by the host-side Jackin owner. The agent or a Docker child must not be able to send an unauthenticated request that opens an arbitrary URL or reveals an arbitrary host path. No PTY, stream, or volume probe proves these authorizations. Account identity, private home isolation, supplementary groups/capabilities, global vs workspace account inventory, selected model/effort, usage attribution, and account-revision reconnect behavior all remain unproven at runtime.

Multi-gateway inventory and events need stable target identity. A duplicate display name on two gateways must not select, mutate, or attribute usage to the wrong sandbox. An unreachable target is unavailable, not deleted. Current CLI/source maps indicate target-aware fleet inventory is new retained Jackin host logic, not something supplied automatically by the OpenShell gateway. Prove cross-target selection and event/usage attribution independently.

## Optional Docker authority

Default-off tests against a healthy engine and the external mutual-TLS engine tests are useful evidence for a denial/configuration path and Docker API mechanics. They do not qualify a Jackin-managed engine architecture. The engine grants broad control over its children and can expose application ports independently of the agent's own OpenShell network policy. Docker children do **not** inherit the agent policy by assumption. In the reviewed evidence, host-engine/API identity and application-port reachability are separate boundaries; a test that rejects A's Docker API credential at B does not prove that A cannot reach B's published application port, or vice versa.

Required before choosing this architecture: one owner (Jackin host infrastructure or a clearly specified OpenShell-managed resource) for each dedicated engine, credentials, network, port leases, volume, image cache, child, and cleanup action; default-off proof; explicit grant/readback; TLS positive/negative cross-instance tests; concurrent fixed/dynamic port allocation, collision/exhaustion/reuse and callbacks; online pull/build with registry credentials; actual edited Cargo/nextest Testcontainers path; and stop/restart/eject/exile/purge and crash-recovery behavior. If the external daemon remains outside OpenShell, it remains an **external component** and must still be managed by the replacement design. The statement “OpenShell is the only execution system” does not make an unowned daemon fixture an acceptable product design.

## Component-size assessment and next proof

Potentially narrow OpenShell upstream change: add immutable sandbox identity/generation preconditions to stop/start/delete (and any other name-targeted mutation), with one positive test and a stale same-name negative test. Until built and executed, the released failure remains.

Not a small patch: durable Jackin resource intent/reconciliation, safe host-workspace authorization and TOCTOU control, a managed dedicated-engine lifecycle with port/network isolation, account-scoped credential/state retention, target-aware inventory, Capsule-equivalent session and host-action authorization, and per-target driver/profile enforcement. These need retained host components or upstream architectural interfaces; no new subsystem should be simulated by a one-off experiment.

The next smallest decisive path is sequential: (1) resolve stale mutation identity with a narrow released-vs-patched test; (2) test Candidate B as an actual session protocol including account separation, authorization, interruption and resume, or stop if it cannot preserve those boundaries; (3) prove atomic/TOCTOU-safe workspace grant-to-volume use and durable cleanup/recovery; (4) execute the selected managed engine path with Testcontainers and cross-instance application-port negatives; (5) only then combine role, credentials, session, workspace, engine, recovery and teardown on each required target. Present tests are primitive evidence only; there is no combined journey, and the required targets remain incomplete.

**Review result:** not ready for a full rewrite. This conclusion is independent of the source mapping and does not classify unexecuted candidates as PASS. It does not infer readiness for any platform from the local OrbStack run.

## Addendum: verification-worker writable-root alternative

This addendum reviews the evidence in `results/full-refactor-20261024/verification-worker/patch-tmpfs/result.md` and its P10/P11 artifacts. The released structured tmpfs path failure and the narrow `HostConfig.Tmpfs` experimental patch are correctly separated. The tmpfs patch retained `noexec`/`nosuid`, enforced the tested capacities, and kept the protected target and volume-admission negatives. P10/P11 remain **FAIL for the declared worker contract**: Docker reports `ReadonlyRootfs:false`; P10 could modify its image-owned `/work/repo`; P11's image workdir is `/sandbox`, `include_workdir:false`, and `/sandbox` is read-only, which denied that particular write, while rootfs stayed mounted read-write. The current report is right not to call the whole worker PASS.

The literal Docker `ReadonlyRootfs:true` flag is an implementation mechanism, not necessarily the user-facing security invariant. If Jackin's required contract is that an untrusted verifier cannot modify image/root files and may write only in bounded `/tmp` and `/build`, a default-deny Landlock policy applied to every untrusted process can in principle preserve that boundary even when the Docker root mount is technically read-write. This is a possible equivalence to test, not a pass inferred from policy YAML or one denied write. If the accepted contract specifically requires a read-only root mount as an independently inspectable property, Landlock is not equivalent and the worker remains blocked on the missing rootfs switch.

The candidate P11 policy lists `/bin`, `/usr`, `/lib`, `/proc`, `/dev/urandom`, `/etc`, `/var/log`, and `/sandbox` read-only, with `/tmp`, `/dev/null`, and `/build` read-write, and sets `include_workdir:false`. This looks close to default-deny for the tested layout, but the run record says root mount not read-only and the evidence must prove which exact policy OpenShell applied to the worker process. The protected policy path itself cannot be opened or enumerated as an allowed writable grant. P11 denies `/work/repo` because the path is outside the explicit rules; however, it did not prove that *all* alternate image paths are denied when they are DAC-writable by UID/GID 1000.

Before treating Landlock as equivalent, keep all existing NNP, capability-drop, network, CA, identity and admission settings intact, then run these execution probes with the exact applied policy and exact worker UID/GID:

1. **Default-deny writable-path sweep:** pre-create disposable directories and files in the derived image owned/mode-writable by UID/GID 1000 at `/work/repo`, `/var/tmp`, `/home`, `/dev/shm`, `/run`, `/opt`, `/usr/local`, and any image-specific writable path. Confirm attempts to create, truncate, rename over, chmod, unlink, and write through an already-created file fail everywhere except the exact bounded `/tmp` and `/build` grants. Include hard links where the filesystem permits, nested directories, dangling and retargeted symlinks, `..`, bind/mount aliases if the driver permits, and same-directory atomic replacement.
2. **Privilege/descriptor boundary:** prove the launched untrusted PID and each descendant remain under Landlock after fork/exec; inspect effective UID/GID, supplementary groups, capability sets, `NoNewPrivs`, seccomp and Landlock state. Verify no inherited writable file descriptor, directory FD, Unix control socket, or pre-opened path handle reaches the verifier. Use an adversarial child process and test `/proc/self/fd` plus attempted fd-based write to a protected canary. A denial on a fresh pathname does not test descriptors opened before restriction.
3. **Agent-side and supervisor separation:** demonstrate that the agent/verifier cannot ask a trusted supervisor/helper to write arbitrary rootfs paths or obtain a privileged fd. Confirm control sockets are not mounted or reachable to the worker unless specifically authorized. Test user namespaces, setuid binaries, file capabilities and `execve` of writable paths while retaining existing NNP/capability restrictions; do not add privilege or weaken controls to make a negative pass.
4. **Bounded writes and persistence:** positively fill `/tmp` and `/build` to their configured byte limits and show writes outside them denied. Check writable tmpfs doesn't let a process hide persistent output or exhaust unbounded backing memory; measure aggregate memory including tmpfs and worker. Re-run network, source/check bundle read-only, timeout/cancellation, output caps, CPU/PID and memory limit probes with the identical policy. Investigate the memory code 247 result with cgroup/OOM evidence rather than treating it as either pass or product failure.
5. **Startup and policy identity:** record the immutable image digest, image-declared `WORKDIR`, effective OpenShell policy revision/hash, mount table, driver config and process ancestry. Prove no race between policy setup and first worker instruction, and fail closed if Landlock is unavailable or incomplete. On supported targets, require equivalent kernel enforcement; do not infer macOS/VM/Kubernetes behavior from this Linux/OrbStack process run.

Landlock reduces the need to insist on the literal `ReadonlyRootfs` flag only if the entire untrusted-process boundary is covered and these negatives pass. If any writable escape, inherited descriptor, helper-mediated write or platform gap appears, keep the worker FAIL and require either the rootfs mount capability or another proven enforcement boundary. This is an architecture equivalence review; no new runtime test was run here.
