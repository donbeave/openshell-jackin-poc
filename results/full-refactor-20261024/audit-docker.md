# Jackin Docker and image-builder source audit

**Audit type:** pinned-source trace, not a runtime test. **Jackin:** `6e266406b49da2ab3c55355f3b7d33d1643ee6cd` (immutable snapshot at `experiments/full-refactor-20261024/source/jackin`). **Result:** source-mapped; no PASS is claimed for OpenShell. This audit is about preserving user-visible behavior during a fresh OpenShell rewrite. It does not design legacy Docker-state import.

## Scope and interpretation

Jackin's Docker use currently combines two distinct authorities: (1) a host Docker engine that builds images and also runs Jackin agent containers, and (2) an optional per-role Docker-in-Docker engine. The rewrite must separate those. Docker may remain the launch-time image builder; OpenShell must own agent sandbox execution. Optional sandbox Docker must remain off by default and be independently authorized. Existing results from the earlier POC use a different Jackin revision and are not runtime evidence for this pinned audit.

Paths and line numbers below are relative to the pinned Jackin snapshot. Caller names identify production paths; `crates/**/tests/**`, inline test modules, docs, manifests, and build/release tooling are separately classified below. The broad raw source indexes are `docker-api-production-calls.txt`, `docker-cli-production-calls.txt`, and `audit-docker-rawmatches.txt`; they are search evidence, not a substitute for the call trace here.

## Host Docker CLI and packaging inventory

`docker-cli-production-calls.txt` records direct command/env matches beyond Bollard: `docker run` for selected-agent version probing (`image/version.rs`); image build/tag/buildx and `docker info` (`jackin-runtime-image`, `jackin-image`); Docker version preflight; Docker security-options diagnostic; workflow verification image/containers; console/restore inspections; and xtask/build/release operations. Each production call must be migrated by action, not removed because it occurs in a Docker-named crate.

`docker/construct/Dockerfile` installs Docker CLI, Buildx and Compose in Jackin's published construct/role tooling image. This is an installed-tool capability for users/role hooks, not proof that the host engine is in the sandbox. Preserve required tools in the derived role image; authorize Docker API access only for the optional Docker profile. `docker-bake.hcl`, `crates/tools/jackin-xtask/src/construct.rs`, image publication scripts, and related CI are build/release machinery and should remain or be deliberately redesigned as build operations. `Cargo.lock`, Cargo manifests and package-group policy describe dependency/build edges, not production execution; do not remove a crate wholesale without migrating callers and retained generic interfaces.

## Search exclusions and classification rules

The broad index includes many non-runtime hits. Exclude them from production-callsite counts while retaining them in `audit-docker-rawmatches.txt` for auditability:

- `crates/**/tests/**`, `#[cfg(test)]` modules, fake Docker clients and command-recording tests: evidence about intended behavior, not executed Docker production paths.
- `docs/**`, README/examples, changelogs and generated docs: user explanation, not executable runtime implementation.
- `Cargo.lock`, `Cargo.toml`, policy package manifests and build metadata: dependency declarations only.
- `docker/construct/**`, `docker-bake.hcl`, `xtask` image publication/build and CI lanes: build/release responsibility, not runtime adapter; retain as validation/build tooling.
- Generic command-runner, logging, telemetry strings, user-facing Docker error text, labels or domain names without a production engine action: not independently a Docker runtime call.

No production source inspection here establishes runtime compatibility, OpenShell API coverage, security parity, or successful migration. Those require execution evidence in the follow-up experiment directories.

## Source-only conclusion and next smallest proofs

The runtime migration is not a crate rename. The highest-risk sequence is (1) build the real Architect-derived selected-agent image at launch with the separate host builder, deliver it by digest to a fresh gateway, and start it with explicit command; (2) run Jackin session/control path and verify stable identity/lifecycle; (3) prove workspace/state paths and profile grant boundaries; (4) separately test default-off and explicitly granted dedicated Docker engine; (5) prove owner-aware cleanup and cache pruning. Docker-specific service calls and user flows above are source-mapped only. This audit makes no overall readiness verdict.
