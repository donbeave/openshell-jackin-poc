## Scope and ownership rule

Jackin remains owner of role/workflow semantics, verification policy and result binding, host UX/CLI/JSON compatibility, target selection, account/UI state, durable workflow history, and host diagnostics. OpenShell is a candidate owner for sandbox process execution, sandbox lifecycle and status, policy enforcement, image delivery, and optional separately granted Docker capability. A replacement must not add host/Docker fallback for verification. Existing 6e code has a Docker-backed verification worker, so replacing its execution mechanism is required even if other runtime operations map cleanly.

## Inactive, incomplete, and future foundations

- Multi-gateway target routing/inventory is absent from current CLI; existing path-valued `LoadArgs.target` means workdir or saved workspace, not runtime target (`cli.rs:30-43`). This is a new Jackin host responsibility.
- Runtime discovery symbols are not a multi-gateway product workflow. The raw search resolves use to generic role-name enumeration for cleanup/DinD-GC and exports; no user-facing target selection caller found.
- Workflow HostGrant compile-time maxima are not proof that these limits reach a sandbox; no runtime grant consumer/readback was found in this audit.
- Preservation-hold reads exist, but a normal producer path was not found; cancellation sentinel is separate workflow metadata.
- Checkpoint metadata is not backup, and an event record is not an OpenShell runtime event. These distinctions must stay explicit.
- Findings in `rawmatches/cli-host-fleet.txt`, `host-lifecycle-targets.txt`, `selected-operations.txt`, and `verify-worker.txt` include tests, docs, examples, build/config files, and inactive symbols. The classifier is a navigation aid, not an evidence claim. Their tests were not executed for this audit.
- Windows and future collaboration capabilities are outside this source audit’s runtime proof; no result is inferred.

## Bounded next experiment: OpenShell verification worker

Use the existing v0.1.5 gateway/client fixture, a fresh Jackin workflow candidate, actual frozen `TestPolicy`, and the pinned Python image. Jackin host code prepares the one-use candidate checkout and trusted bundle exactly as current service does; do not implement a host/Docker fallback. Create one OpenShell sandbox per test, run argv exactly, collect bounded stdout/stderr and exit status, then delete and query for deletion. Record image/target/sandbox IDs, policy hash, effective limits, network probe, write probes, credential absence, cancellation, and cleanup. Add negative probes for network, rootfs writes, forbidden caps, excess memory/PIDs, wrong digest, wrong candidate/run version, duplicate result and deletion failure. Compare observed limits against current Docker invocation. If any required control cannot be configured or read back, stop and mark the worker contract blocked; do not loosen current profile. This experiment tests the highest-risk active workflow dependency and is not production implementation.

## Audit result

This audit identifies a bounded architecture candidate, but source mapping is not runtime evidence. The active verification worker still requires a full execution equivalence experiment, target-aware Jackin host control is new work, checkpoint persistence/hold semantics remain unresolved, and broad lifecycle/status/session behavior needs integrated execution proof. No readiness verdict is issued from source inspection.
