## User entry and backend routing

`jackin load` is the user entry. `crates/apps/jackin/src/app/load_cmd.rs:57-60,168-193` resolves the request and calls `runtime::load_role`. `crates/services/jackin-runtime/src/runtime/launch/launch_pipeline.rs:1380` resolves a backend after role/image planning. `crates/services/jackin-runtime-launch-mounts/src/mounts.rs:709-733` selects workspace `runtime.backend`, falling back to host-wide `runtime.default_backend`; accepted strings are `docker` and `apple-container`. This is configuration selection, not an OpenShell feature. Jackin owns the role selector, workspace selection, and user-facing commands; a rewrite should keep those behaviors and remove this runtime selector when OpenShell is the sole executor.

The selected Apple route is active code: `crates/services/jackin-runtime/src/runtime/launch/launch_pipeline/launch_core/orchestrate/runtime.rs:112-137` builds workspace/agent mounts, runs the earlier Docker cleanup guard, calls `runtime::apple_container::launch`, and returns `RuntimeDispatch::AppleContainer`. `finish.rs:32-45` returns the instance name immediately for this variant. The Apple launch does not go through Docker `launch_role_runtime`; this early return is a material boundary for resource grants and finalization.

## Current status distinctions

- **Active in code, runtime not proven here:** backend selection; image-to-provider launch; CLI run/list/start/stop; guest wait, PTY attach, reconnect/status; per-instance mounts and usage relay; Apple manifest dispatch; stop/eject/purge guard/exile enumeration; workflow checkpoint metadata record; Capsule force-daemon marker; Darwin process reaper call path.
- **Known incomplete or absent in production path:** Apple `finalize` returns the explicit Phase 0 error; fresh Apple dispatch skips Docker finalization; generated provider config overlays and worktree auxiliary overlays reject; Apple `caps_add` is empty; no CPU/memory/process/fd limit request; no Apple VM sizing/create/delete API; snapshot is Docker-exec-only; Apple provider/API target has no live runtime result in this audit.
- **Foundation/no production caller or non-equivalent behavior:** Apple `remove`/`remove_with`/`rm` exists in the client/backend surface but no production caller was found; `eject` stops and the purge guard checks inventory, so this does not establish Apple runtime-object deletion. Full Docker inspection/readback and `compare_grant_vs_actual` are uncalled foundations; launch supplies `workflow_grant: None`; `capture_checkpoint` is only defined and unit-tested, not production-called. Workflow checkpoint metadata is distinct from source capture and VM snapshots. No live-write barrier is required from these foundations alone. Source hooks and adapter crates compiling do not prove target runtime behavior; design docs describing rootless DinD/caps/mounts are plans, not working support.
- **Exclusions:** docs, roadmap, research, README, tests/fake clients, Cargo/workspace membership, architecture gates, generated source metadata, and CI static repository checks establish intent or build structure only. They are not production runtime callers or execution evidence.

## Rewrite compatibility consequence

No import/migration of Apple Container manifests or old runtime state is required: approved fresh setup/reset can discard those old records. New Jackin persistence and recovery remain requirements. The OpenShell-backed state must identify target/gateway, immutable sandbox identity/generation, role/image revision, workspace authority, retained project/agent data, credentials/account revision and session resume data. Runtime deletion must not imply retained-state deletion. A host bind failure on the tested packaged OpenShell VM profile remains independent execution evidence and is not cured by this source audit.

## Result

**Source classification only; no PASS.** Apple Container is an active but explicitly experimental selectable runtime, with incomplete finalization and unproven VM/mount/resource behavior. A full OpenShell replacement can remove Apple Container and its CLI adapter, but must reimplement Jackin's user-facing lifecycle/session/data contracts over OpenShell and preserve image-at-launch, host workspace/state authority, credential behavior, profile boundaries, usage/session reporting and recovery. Exact OpenShell parity still depends on runtime tests and target coverage elsewhere in the evidence set.

## Foundation/caller correction

Independent review found the full Docker readback and source capture were being overstated. Caller searches and all matches are appended in [audit-apple-vm-rawmatches.txt](audit-apple-vm-rawmatches.txt). Review: [source-coverage-review.md](source-coverage-review.md).

- `inspect_full_container_by_id`: only `DockerApi` trait/default and Docker adapter implementation; no production invocation.
- `compare_grant_vs_actual`: definition/re-export and unit tests; no production invocation. Launch initializes `workflow_grant: None`.
- `capture_checkpoint`: definition plus unit tests only; no production caller. Active `record_checkpoint` stores workflow checkpoint metadata; it does not invoke source capture and does not create a VM snapshot.
- Effective Docker profile application and cgroup/AppArmor probes remain separate active code. Apple route bypasses Docker profile setup. OpenShell still must enforce active profile contracts. Readback/live-write barriers are not blockers solely because inactive helper foundations exist.
